CellAg — Architecture Overview

An end-to-end agent for cellular-agriculture media work. One conversation, one canonical state, two scientific-domain frameworks (composition + validation), 50 tools across two MCP servers.

github.com/harragi/CellAg · MIT · written for the team to skim before sitting down at the running app.

TL;DR

The CellAg agent takes a natural-language query — typically "design a media for X cell type and validate it against Y" — and runs it through a design → validate loop end-to-end, in a single conversation. Two markdown notes files act as canonical project state. The agent reads them every turn, calls scientific-database tools to ground its reasoning, and proposes structured section edits the user reviews inline before they hit disk.

The agent runs locally: a Bun + TypeScript backend on port 3001, a React + Vite UI on port 5173, both kicked off with bun run dev. It uses the Claude Agent SDK for the model loop and exposes its own custom tool set via an in-process MCP server, plus a curated subset of ToolUniverse's 2,200-tool catalog via a second stdio MCP server. The user sees streaming text, color-coded tool cards, a step timeline on the left, and inline propose-edit cards in the chat.

Selection rule

The system prompt tells the agent: "if a TU tool exists, prefer it; the generic query_* wrappers are fallbacks for novel paths." The custom wrappers stay around because they're flexible (any endpoint, any params), but the named TU tools are easier for the model to use correctly.

Request lifecycle

What happens when you click send:

1
Browser → POST /api/chat with { message: "…" }.
Browser opens a fetch with Accept: text/event-stream; the response body becomes the SSE stream.
2
Server appends user turn to history; assembles system prompt.
Reads both SKILL.md files and both notes.md files fresh each turn (~10K tokens cached after first call). Returns one long composite string.
3
Server starts query(...) with both MCP servers wired.
mcpServers: { science: in-process, tooluniverse: stdio subprocess }. allowedTools: [glob + 40 explicit names]. maxTurns: 24.
4
SDK emits system/init message. Server pushes it through SSE.
Browser sees both MCP servers as connected. Status dot in header turns amber.
5
Model emits tool_use blocks; SDK runs the handlers automatically.
Each tool call is forwarded to the SSE stream as type: "assistant" with a tool_use content block. Browser adds a tool card to the chat list and a numbered step in the rail (color-coded by family).
6
Tool handlers fetch (KEGG, BiGG, …) or read local files (notes, caail).
SDK feeds each result back to the model as tool_result. Server forwards to UI; browser updates the matching tool card from "running…" to "done"/"error".
7
If the agent calls propose_notes_edit: handler stages the edit in-memory and emits event: proposed_edit on the SSE stream.
Browser pushes a propose-edit card into the chat with apply / reject buttons. The edit is NOT yet on disk.
8
Model finishes; SDK emits type: "result" with cost, turn count, stop reason. Server pushes event: turn_end, then event: done, then closes the stream.
Browser flips streaming bubble to non-streaming, status dot to green.
9
User clicks apply on a proposed edit. Browser → POST /api/notes/apply { editId }.
Server looks up the edit's target_file, appends a date-stamped block to the right notes.md, drops the edit from the staging map. UI refreshes the card to applied.
Keepalives

Bun's idleTimeout defaults to 10 seconds. Long agent turns (3-5 minute multi-tool runs) would otherwise drop. We bump to 255s and emit a : keepalive <timestamp> SSE comment every 15s — invisible to the UI, keeps the connection live.

Propose-then-apply flow

The agent never writes to notes.md directly. Every change is two-phased: the agent stages, the human approves.

1. Agent calls propose_notes_edit

  • target_file: "sardine" | "hamster"
  • section: "§6 Validation workflow — …"
  • new_content: markdown
  • rationale: why

2. Server stages

  • Inserts into state.proposedEdits: Map<id, ProposedEdit>
  • Emits event: proposed_edit on the SSE stream
  • Tool returns "Edit X staged for review"

3. UI shows inline diff card

  • Card in chat with target file, section, rationale, full new_content
  • Apply / Reject buttons attached

4. User decides

  • Apply → POST /api/notes/apply → server appends date-stamped block to the right notes.md → UI marks card "applied"
  • Reject → POST /api/notes/reject → server drops the staged edit and injects a system note into history so the agent doesn't retry
Why append-only

The MVP applies edits as date-stamped blocks at the bottom of notes.md rather than surgically replacing the named section. The agent's section field and rationale are preserved in the appended block (HTML comment marker + level-3 heading), so you can fold the change into the right section manually later. This trades polish for safety — section-precise replacement requires a robust markdown editor I didn't want to risk for a smell-test build.

Skills layer

Six Claude Code skills under .claude/skills/. Two of them (the driver skills) are loaded verbatim into the agent's system prompt every turn. The four others are available when working in this workspace through the Claude Code CLI.

The router and sub-drill-down skills exist so a Claude Code session in this workspace can pick the right operating manual for a focused conversation. The agent app at :5173 uses the two driver skills directly — both are always loaded, regardless of the kind of question.

How to run

git clone https://github.com/harragi/CellAg.git
cd CellAg/InsilicoMediaDesign/ProjectSardine/agent

# install
(cd server && bun install)
(cd web && bun install)

# configure
cp .env.example .env   # then fill in ANTHROPIC_API_KEY

# install ToolUniverse (the MCP subprocess)
uv tool install tooluniverse

# boot (two terminals)
(cd server && bun run dev)   # → :3001
(cd web && bun run dev)      # → :5173

open http://localhost:5173

That's it. The Welcome screen lists the canned prompts; click one to watch the loop run.
